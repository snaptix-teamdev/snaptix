# Архитектура проекта

Проект построен по принципам Feature-Sliced Design (FSD).
Архитектура разделяет код по слоям ответственности и ограничивает связи между ними.

## Стек

- NextJS (в т.ч. app router), React (hooks)
- TypeScript
- TanStack Query — server state
- Radix - UI
- Module CSS

## Слои архитектуры

### `app`

Слой инициализации приложения. Содержит всё, что необходимо для запуска приложения.

Ответственности:

- точки входа
- роутинг
- глобальные провайдеры
- глобальные стили

Пример:

```
src/
  app/
    layout.tsx
    providers/
    styles/
    page.tsx
```

### `pages`

По fsd: Полные страницы приложения или крупные части страницы при вложенном роутинге. Находятся на верхнем уровне.

! но в Next.js файловый роутинг и layout-иерархия App Router !

Рекомендуемый паттерн:
Бизнес-страница лежит не в app, а в src/pages.

При использовании Next.js App Router вместе с FSD принято держать папку app очень тонкой. Она отвечает только за роутинг и инфраструктуру Next.js, а вся логика и композиция UI живёт в слоях (pages, widgets, features, и т.д.).

! Все специальные файлы Next.js остаются в app/, но они должны быть максимально "тонкими" — только композиция и делегирование логики в FSD слои !

Правило:
Если файл требуется Next.js роутером → он живёт в app.
Если это UI или логика → он живёт в FSD слоях.

Пример:

```
src/
  app/           # Next.js роутинг (export default, требование фреймворка)
    dashboard/
      page.tsx   # export { DashboardPage } from '@/fsd-pages/dashboard'

  fsd-pages/     # FSD слой pages
    dashboard/
      ui/
        DashboardPage.tsx
```

```
import { DashboardPage } from "@/fsd-pages/dashboard";

export default function Page() {
  return <DashboardPage />;
}
```

Страница:

- композирует widgets и features,
- управляет состоянием страницы,
- не содержит доменной бизнес-логики.

#### Сегменты `pages/*`

- **ui** — React-компоненты страницы
- **lib** — вспомогательные функции, используемые только в рамках страницы
- **constants** — константы страницы
- **model** — UI-состояние страницы
- **api** — взаимодействие с бэкендом (если требуется)

##### `model`

Используется для:

- фильтров
- сортировки
- пагинации
- selection
- состояния модалок
- оркестрации поведения страницы
- TypeScript-типов (interfaces / type)

Структура:

```
model/
  types/
  scheme/
  zod/
  stores/
```

##### `api`

Сегмент для запросов страницы и связанных с ними контрактов.

Что храним в `pages/*/api`:

- `apiService.ts` — клиент, функции запросов
- `dto.ts` — DTO/типы контрактов бэкенда (запрос/ответ)
- `hooks/*` — React Query хуки (`useQuery`, `useMutation`) для этой страницы

Пример

```
pages/zones/
  api/
    api.ts
    dto.ts
    mappers/
    hooks/
      useUpdateZoneMutation.ts
```

### `widgets`

Крупные, самодостаточные блоки интерфейса, обычно реализующие целый пользовательский сценарий.
Сегменты аналогичны `pages`.

Примеры:

- панель управления,
- таблица пользователей с фильтрами,
- карточка с набором действий.

Widget:

- может использовать features и entities,
- может иметь собственное состояние,
- не является страницей.

### `features`

Переиспользуемые пользовательские действия, которые приносят бизнес-ценность.
Отвечает на вопрос: Что пользователь делает?
Сегменты аналогичны `pages`.

Примеры:

- поиск
- редактирование пользователя
- блокировка пользователя
- экспорт данных

Feature:

- использует entities,
- может содержать TanStack Query,
- не знает о страницах.

### `entities`

Бизнес-сущности предметной области проекта.

Бизнес-сущность:

- имеет бизнес-смысл,
- используется в разных частях приложения,
- не зависит от конкретной страницы или сценария.

Примеры:

- User
- Order
- Product
- Role

> Entity ≠ «данные с сервера».
> Данные могут приходить с сервера, из формы, моков или localStorage.
> Важно бизнес-значение, а не источник данных.

#### Как быстро понять: это entity или “данные страницы”

Задай себе вопрос: “Если завтра появится другая страница/виджет, где тоже нужна эта сущность — мне будет естественно переиспользовать этот код без переделок?”

- **Да** → скорее всего это **entity** (доменная модель, типы, маппинг, селекторы, базовые запросы сущности).
- **Нет** → скорее всего это **данные/модель конкретной страницы** (view-model под таблицу/форму, DTO именно этого экрана, фильтры/сортировки/колонки, специфичный endpoint под UI).

Подсказка по неймингу:

- `User`, `Order`, `Product` → обычно **entities**
- `UsersTableRow`, `OrdersPageFilters`, `ProductListResponse` → чаще **pages/widgets**

#### Пример: `entities/user`

```
entities/user/
  api/
    api.ts        // функции запросов, тонкий клиент запросов (без состояния)
    dto.ts        // DTO от бэкенда
    mapper.ts     // dto -> domain (опционально)
  model/          //доменная модель сущности
    store.ts     // стор сущности (опционально)
    types.ts     // доменные типы
    hooks/       // react-query хуки
```

### `shared`

Переиспользуемый код, не привязанный к конкретной бизнес-сущности.

Примеры:

- UI-kit
- HTTP-клиент
- утилиты
- конфигурации
- общие типы
- конфигурация приложения

```
shared/
  ui/
  api/
  lib/
  config/
  constants/
  types/
```

## Краткие правила

- `pages` — композиция страниц и page-level состояние
- `widgets` — крупные UI-блоки
- `features` — пользовательские сценарии
- `entities` — бизнес-сущности
- `shared` — общий фундамент
- слои не импортируют друг друга “вверх”

---

## `index.ts` (Public API слайса)

`index.ts` используется как публичный API слайса.

Основное правило

- `index.ts` создаётся на верхнем уровне каждого слайса
- используется во всех слоях кроме `app` и `shared`
- через `index.ts` наружу экспортируется только то, что действительно должно использоваться извне

Слайс должен выглядеть как **чёрный ящик**, экспортируем **только публичную часть слайса**, а не всё подряд.

### Итог

Каждый слайс должен иметь:

```
slice/
  ui/
  model/
  api/
  index.ts  ← публичная точка входа
```

"use client" превращает компонент в Client Component

## Storybook и unit-тесты

Размещают рядом с компонентом внутри того же слайса. Часто кладут не в pages(обычно композиция), а в:

- shared/ui
- entities/ui
- features/ui
- widgets/ui

## Импорты

1. Если импорт внутри того же слайса — используем относительный путь.
2. Если импорт из другого слоя/слайса — используем абсолютный путь.

Пример:

```ts
// ✅ из другого слайса — абсолютный импорт
import { Chart } from '@/widgets/Chart'

// ✅ внутри слайса — относительный импорт
import { Chart } from './chart/Chart'
```

## Нейминг (сегменты, слайсы, папки)

- Слайсы и папки внутри сегментов называем **с маленькой буквы**.
- Если в названии несколько слов — используем `kebab-case`.

## Стиль кода и нейминг (переменные, константы, компоненты)

- **Весь код** пишем в `camelCase`.
- Константы, значения которых известны заранее (до выполнения кода) — в `UPPER_SNAKE_CASE`:
- Названия React-компонентов — `PascalCase`
- утилиты/хуки — `camelCase.ts`
